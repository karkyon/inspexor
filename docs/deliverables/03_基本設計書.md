| 構成要素 | 役割 |
|---|---|
| Web アプリ（Cloud Run） | 画面の表示と、データの登録・参照を受け付ける窓口（API）。ログイン・権限の確認を行う |
| 帳票作成（Cloud Run） | 確定した報告から日報PDFを作成し、Cloud Storage に保存する |
| Firestore | 報告・マスタ・利用者・変更の記録などを保存するデータベース |
| Cloud Storage | 日報PDFと、毎日のバックアップを保存する。外部へは公開しない |
| Cloud Scheduler | 毎日 3時15分にバックアップを起動する。帳票作成の取りこぼしを拾うため、15分ごとに帳票作成を起動する |
| Secret Manager | ログインの暗号化に使う鍵などを保管する |
| 予算アラート | クラウド利用料が設定額を超えそうなときにメールで通知する |

Cloud Run は「使われていない時は台数0台」に設定し、利用料を抑えます。このため、しばらく使わなかった後の最初の表示は数秒かかります（提案書の構成と同じ性質です）。

## 3.3 画面の共通ルール

| 項目 | ルール |
|---|---|
| 入力エラー | 項目の近くに理由を表示し、画面上部にもまとめて表示する（項目へ移動できる） |
| 必須・任意 | 項目名の横に「必須」「任意」を表示する |
| 二重押し | 確定ボタンは押した後、処理が終わるまで押せない |
| 通信切れ | 画面上部に表示を出し、確定ボタンを押せなくする。入力は下書きとして残る |
| 同時更新 | 他の人が先に更新していた場合は保存せず、再読込を促す。作業中の日報の従事行の追加・終了は行ごとの操作のため、別の iPad で同時に操作しても他の行を消さない |
| 権限 | 区分にない画面は「この画面を表示する権限がありません」と表示する |
| 自動ログアウト | 30分操作がないか、ログインから12時間でログイン画面へ戻る |
| 本人確認 | パスワード再設定・代理入力など重要な操作で、直近10分以内の認証がなければ本人確認の画面（パスワードの再入力）を開き、確認後に同じ操作を1回だけ送り直す |
| 見やすさ・使いやすさ | WCAG 2.1 AA に合わせる。文字と背景の色の差 4.5:1 以上、最初の Tab で「本文へ移動」、入力の誤りは読み上げソフトにも伝える。画面の変更のたびに自動検査（axe）で違反0件を確認 |
| 画面ごとの詳細 | 表示・入力項目、入力規則、操作、メッセージは画面設計書（SK-2026-08-MINI-10）に記載 |

# 5. データ設計（概要）

## 5.1 データベースの方式

データは Firestore に保存します。Firestore は表の代わりに「コレクション（同じ種類の文書の入れ物）」と「文書（1件分のデータ）」でデータを持ちます。読み書きの回数で課金され、小規模な利用では無料枠に収まります。

## 5.2 コレクション一覧

| 区分 | コレクション | 内容 |
|---|---|---|
| 利用者 | users | ログインID、氏名、区分、パスワード（復元できない形）、ロック状態、権限の変更日時 |
| マスタ | customers / customerContacts / products / workTypes / defectTypes / workers / workLocations / vehicles / holidays | 各マスタ（品番の工程・在庫の設定、作業内容の既定の検査区分・作業場所、作業場所の「お客様の工場」、担当者の部署名を含む） |
| 報告 | workReports（作業日報）、deliveryReports（運搬実績） | 報告番号、状態、版、運搬費、一覧・集計用の要約、代理入力の記録 |
| 報告の版 | workReports/{id}/revisions、deliveryReports/{id}/revisions | 版ごとの入力内容。作業日報は従事行（laborLines）と品番の明細（items）。確定した版は書き換えない |
| 在庫（範囲外） | inventoryTxns、inventoryBalances | 在庫の動き（追加のみ）と品番ごとの残高・検品ロット |
| 帳票 | documents、files、templateVersions | PDF の作成状況、作成したファイルの保存場所と確認用の値、様式の版 |
| 処理の受け渡し | outbox | 「確定した」などの出来事を帳票作成へ渡す |
| 補助 | uniqueKeys、counters、idempotency、rateLimits | 重複登録の防止、報告番号の採番、二重送信の防止、ログイン回数の制限（期限で自動削除） |
| 記録 | auditEvents | 誰が・いつ・何をしたか（追記のみ） |

## 5.4 データを守る仕組み

| 仕組み | 内容 |
|---|---|
| 版の保存 | 確定した版は書き換えず、修正は新しい版として追加する |
| 同時更新の防止 | 文書ごとに更新番号（version）を持ち、画面で読み込んだ番号と違えば保存しない |
| 重複の防止 | ログインID・マスタのコード・報告番号が重ならないよう、登録と同時に専用の文書（uniqueKeys・counters）を作る |
| 二重送信の防止 | 確定・再出力の要求には要求ごとの番号を付け、同じ要求は1回だけ処理する |
| 変更の記録 | 登録・確定・修正・運搬費・マスタ・帳票の操作を auditEvents に追記する（変更・削除の手段を持たない） |
| 直接アクセスの禁止 | Firestore・Cloud Storage は、システムの実行用アカウント以外からは読み書きできない設定にする |

# 6. 処理方式

## 6.1 確定から日報PDFまで

| 順 | 処理 | 場所 |
|---|---|---|
| 1 | 画面で「確定」を押す | iPad |
| 2 | 入力内容を再チェックし（全員の従事行が終わっていること、同じ作業者の時間の重なりがないこと）、従事行から時間の合計をサーバーで計算して確定。「確定した」出来事を outbox に書く（すべて1回の処理で行い、途中で失敗したら何も残さない）。報告番号は作成時に採番済み | Web アプリ |
| 3 | 確定の直後に帳票作成を呼び出す（Google の認証付き） | Web アプリ → 帳票作成 |
| 4 | outbox の出来事を読み、PDF を作成して Cloud Storage に保存。報告の状態を「提出済」にする | 帳票作成 |
| 5 | 失敗したときは 10秒・30秒・2分・10分・30分の間隔で最大5回やり直す。それでも失敗した場合は「帳票エラー」とし、事務所が再出力する | 帳票作成 |
| 6 | 呼び出しが届かなかった場合とやり直しに備え、15分ごとに、残っている出来事を処理する | Cloud Scheduler → 帳票作成 |

## 6.2 報告の状態

| 状態 | 意味 | 次の状態 |
|---|---|---|
| 下書き（DRAFT） | 入力中、作業中（終わっていない従事行がある）、または事務所の修正中 | 確定、破棄（確定したことのない下書きだけ） |
| 確定（CONFIRMED） | 確定済み、PDF 作成待ち | 提出済 |
| 提出済（SUBMITTED） | PDF 作成済み | 修正で「下書き」（新しい版） |
| 破棄（DISCARDED） | 誤って作った作業日報を破棄した。一覧（初期の条件）・集計の対象外。記録は残る | — |

「作業中」は状態ではなく、下書きのうち終わっていない従事行があるものを指します（一覧の絞り込みと現場ホームに表示）。承認・差戻し・請求確定の状態はプログラム上に用意していますが、今回は使いません。

## 6.3 バックアップ

| 項目 | 内容 |
|---|---|
| 対象 | Firestore の全データ（PDF は Cloud Storage に保存済みのため対象外） |
| 方法 | Cloud Scheduler が毎日 3時15分に Firestore の書き出し（エクスポート）を起動し、Cloud Storage のバックアップ用バケット（inspexor-jadeworks-prod-backups）に保存 |
| 保管 | 30日（31日目に自動削除） |
| 復旧 | 書き出したデータを Firestore に読み込む（運用・保守手順書を参照） |

## 6.4 セキュリティ方式

| 項目 | 方式 |
|---|---|
| 通信 | すべて HTTPS |
| ログイン | ログインIDとパスワード。パスワードは Argon2 で保存。5回失敗で15分ロック。存在しないIDか誤パスワードかを区別しないメッセージ |
| 回数の制限 | ログイン・本人確認は同じログインIDで10分に30回、同じ接続元から10分に100回まで（Firestore で数え、複数のサーバーで共有）。操作の API は利用者ごとに1分に更新120回・参照600回まで。超えたら一定時間待ってもらう（429） |
| 本人確認 | パスワード再設定・代理入力などは、直近10分以内のログインまたはパスワードの再入力が必要 |
| 管理者の多要素認証 | プログラムに用意（認証アプリの確認コード）。今回は本番で無効にし、お客様のご判断で有効にする |
| ログイン状態 | 署名付きの Cookie（HttpOnly・Secure・SameSite=Lax）。30分無操作または12時間で失効。利用停止・区分変更・パスワード再設定で即時に失効 |
| なりすまし送信の防止 | 更新系の要求にはログインごとの確認用トークン（CSRF トークン）を必須にする |
| 権限 | API ごとに利用できる区分を決め、サーバー側で確認する。現場の利用者は自分の報告だけを参照できる |
| PDF | 公開しない保存場所に置き、権限を確認したうえで10分間有効なリンクを発行する |
| 鍵 | Secret Manager に保管し、プログラムに書かない。本番と開発で別の鍵 |
| 実行用アカウント | Web アプリ・帳票作成・定期起動・イメージ作成で別々のアカウントにし、必要な権限だけを与える |
| データベースの保護 | Firestore の削除保護を有効にする |
| 個人情報の最小化 | 変更の記録には備考の本文を残さない |
