# 3. 利用者の管理

利用者の追加・変更は、管理者の区分を持つ方が「利用者管理」画面で行います（操作マニュアル 4.9）。当方への依頼もできます。

| 作業 | 管理者が画面で行う | 当方に依頼する場合（メール） | 目安 |
|---|---|---|---|
| 追加 | 利用者を追加し、表示されたパスワードを本人に伝える | 氏名、区分（現場／事務所／管理者／監査） | 2営業日以内 |
| 区分の変更 | ロールを変えて保存（本人は再ログインが必要） | 氏名、変更後の区分 | 2営業日以内 |
| 利用停止（退職など） | 「利用の停止・再開」で無効にする（すぐにログインできなくなる。報告は残る） | 氏名、停止日 | 停止日まで |
| パスワードの再設定 | 「パスワードの再設定」 | 氏名 | 1営業日以内 |
| ロックの解除 | 「ロック解除」（15分待てば自動でも解除） | 氏名 | 当日 |

- パスワードは12文字以上です。メール本文とは別の方法（電話・手渡しなど）で本人に伝えてください。
- 作業者マスタ（作業者・運転者として選ぶ名前）と、ログインする利用者は別のものです。新しい方が入ったときは、必要に応じて両方を登録します。
- 管理者のパスワードを忘れて管理者が誰もログインできない場合は、当方が復旧します。

# 4. マスタの管理

- 追加・修正・無効化は、管理者の区分を持つ方が画面から行います（操作マニュアル 4.8）。
- 使わなくなったデータは削除せず「無効」にします。
- 大量の登録・変更（数十件以上）は、一覧（Excel 等）をいただければ当方で一括登録します（保守の範囲。100件を超える場合は別途ご相談）。

# 5. バックアップと復旧

## 5.1 バックアップの仕組み

| 項目 | 内容 |
|---|---|
| 対象 | すべての報告・マスタ・利用者・変更の記録（Firestore） |
| 時刻 | 毎日 3時15分（日本時間） |
| 保存先 | 本番プロジェクトの Cloud Storage（バックアップ専用、一般公開なし） |
| 保管期間 | 30日 |
| 日報PDF | Cloud Storage に保存しており、削除しません。PDF はデータから再作成もできます |

## 5.2 確認（当方、毎月）

1. Cloud Scheduler のバックアップ処理（inspexor-firestore-export）と帳票作成の起動（inspexor-worker-run）が成功していることを確認する。
2. バックアップ用の保存先に、直近30日分のフォルダがあることを確認する。
3. 3か月に1回、開発用プロジェクトにバックアップを読み込み、報告の件数が一致することを確認する（復旧の練習）。

## 5.3 復旧の手順（当方）

| 場面 | 手順 |
|---|---|
| 誤って報告を修正した | 復旧は不要です。前の版が残っているので、修正（新しい版）で元の内容に戻します |
| 誤ってマスタを無効にした | 画面で修正して有効に戻します |
| データの広い範囲が失われた・壊れた | 1. 利用者に入力の一時停止を連絡 → 2. 失われた範囲と時刻を確認 → 3. その直前のバックアップを Firestore に読み込む（付録 A.3）→ 4. バックアップ後の報告を、紙・PDF・変更の記録から再入力 → 5. 件数を確認して利用再開を連絡 |

最大で前日のバックアップ以降の入力が失われる可能性があります（その場合も、作成済みの日報PDFは残ります）。

# 6. 障害の対応

## 6.1 対応の流れ

| 順 | 誰が | 内容 |
|---|---|---|
| 1 | 利用者 | 操作マニュアル第5章を確認。解決しなければシステム管理者へ |
| 2 | システム管理者 | 複数の人で起きているか確認し、当方へ連絡（1.2 の内容） |
| 3 | 当方 | 受付の連絡、記録（追跡番号）・クラウドの状態から原因を切り分け |
| 4 | 当方 | 復旧作業。Google Cloud の障害の場合は復旧を待ち、状況をお知らせ |
| 5 | 当方 | 復旧の連絡と、原因・再発防止の報告 |

## 6.2 主な障害と対応（当方）

| 症状 | 確認すること | 対応 |
|---|---|---|
| 画面が開かない | Cloud Run の稼働状況、/api/health、Google Cloud の障害情報 | 直前の更新が原因なら前の版に戻す（付録 A.2） |
| 日報PDFが作成されない | documents の状態（FAILED_FINAL）、帳票作成のログ | 原因を直し、事務所から再出力 |
| 全員がログインできない | 鍵（AUTH_SECRET）の設定、Cloud Run の設定 | 設定を戻す |
| 動作が遅い | Cloud Run のログ、Firestore の利用状況 | 設定の見直し |
| 利用料の警告メールが来た | 予算アラートの内容、どのサービスで増えたか | 原因を調べ、お客様に報告 |

## 6.3 業務を止めないために

システムが使えない間は、従来の紙の作業結果報告書に記入してください。復旧後、事務所または現場で入力してください（作業日は実際の日付を選べます）。

# 8. 保守の範囲

提案書 P.15 のとおりです。

| 区分 | 期間 | 費用 | 内容 |
|---|---|---|---|
| 瑕疵保証 | 本稼働開始日から3か月 | 無償 | 合意した要件・仕様と違う動作など、設計・開発が原因の再現できる不具合の調査と修正 |
| 保守 | 保証終了の翌日から33か月 | 月額5,000円 | 操作の問い合わせ、障害の受付と一次切り分け、復旧方法の案内、既存機能の軽微な設定変更・修正、利用者アカウントの管理 |

保守の対象外（別途お見積り）: 機能の追加・仕様の変更、帳票の大幅な変更、大量のデータ修正、誤操作・端末の故障、Google Cloud 等の外部サービスの障害、OS・ブラウザの仕様変更に伴う改修。

# 9. 定期的な保守作業（当方）

| 頻度 | 作業 |

# 付録 A. 当方の作業手順

この付録は保守担当者向けです。

## A.1 本番への反映

1. 変更を当方の作業環境で全テスト（型検査・単体・結合）に合格させる。
2. 開発環境（inspexor-jadeworks-dev）で画面操作テストを全件実行し、合格したら GitHub の main に反映する。
3. main の版から `bash scripts/gcp/deploy-prod.sh` を実行する。イメージを作成し（版の番号は commit 番号）、Cloud Run（inspexor-web・inspexor-worker）、Firestore の索引・アクセス制御、Cloud Scheduler、予算アラートを更新する。範囲外の機能は無効のまま。
4. /api/health、管理者ログイン、報告一覧の表示を確認する。所要時間の計測は `bash scripts/gcp/diag-prod.sh`（業務データは作らない）。
5. 反映内容と日時を変更記録（docs/chg）に残す。

## A.2 前の版に戻す

Cloud Run の「リビジョン」（反映ごとの版）から直前の版を選び、通信の100%をその版に切り替える。データの形式を変えた反映の場合は、戻す前に互換性を確認する。

## A.3 バックアップの読み込み

1. 読み込むバックアップ（日付のフォルダ）を決める。
2. 利用者に一時停止を連絡し、Cloud Run の受付を止める。
3. Firestore のインポート機能で、バックアップを読み込む。
4. 報告の件数・最新の報告番号を確認し、counters（採番）が最新の番号以上であることを確認する。
5. 受付を再開し、利用者に連絡する。

## A.4 利用者アカウントの作成

通常は利用者管理画面（/admin/users）で行う。管理者が1人もいない場合だけ、初期管理者の作成手順（apps/web/scripts/create-admin.ts）で管理者を作る。パスワードはファイルから読み込み、画面やチャット・ログに表示しない。

## A.5 鍵の更新

1. Secret Manager で AUTH_SECRET の新しい版を作る。
2. Cloud Run を新しい版の鍵で反映する（全員のログイン状態と、発行済みの PDF リンクが無効になる）。
3. 動作を確認し、古い版の鍵を無効にする。
